## Scripts

```
npm run dev        # next dev -H 0.0.0.0 -p 3000
npm run build / start
npm run lint       # eslint (next core-web-vitals + typescript + prettier)
npm run test       # vitest (watch)   ·   npm run test:run  # una pasada
npm run format / format:check   # prettier (100 columnas, comillas dobles, trailing commas, plugin tailwind)
```

Variable de entorno: `NEXT_PUBLIC_API_URL` en `.env.local`. Incluye `/api`; el valor por defecto es `http://localhost:3001/api`. Se lee **solo** en `src/lib/api-config.ts` (`API_BASE_URL`), que usan `apiClient`, las páginas públicas (`/register`, `/p/[id]`) y `buildApiPublicFileUrl`. Hasta el 2026-11-16 las páginas públicas no tenían respaldo y, sin la variable, pedían a `undefined/...`.

## Patrones de implementación

**Capa de datos por feature** (`features/<x>/hooks/useX.ts`):

1. Una _query key factory_, **siempre en `shared/api/query-keys.ts`** (auditoría de arquitectura, 2026-11-14; antes cada hook declaraba la suya y las features se importaban entre sí, con ciclos `useTours` ↔ `useTourDashboard` ↔ `useTourSeats`). Las de hoy: (`AUTH_KEYS`, `AGENCY_KEYS`, `AGENCY_BRANDING_KEYS`, `TOUR_KEYS`, `TOUR_SEAT_KEYS`, `TOUR_DASHBOARD_KEYS`, `TOUR_MANIFEST_KEYS`, `BOOKING_KEYS`, `TRAVELER_KEYS`, `PUBLIC_TRAVELER_LOOKUP_KEYS`, `VEHICLE_KEYS`, `VEHICLE_TEMPLATE_KEYS`). Importa la factory en lugar de reescribir la clave y nunca la declares dentro de un hook.
2. Funciones de red puras: `apiClient.get<never, T>(url)`. El segundo genérico es el tipo ya desenvuelto por el interceptor.
3. Hooks `useQuery` y `useMutation`. En `onSuccess`: `invalidateQueries` y `toast.success`. En `onError`: `toast.error(…, { description: error.message })` con el tipo `ApiError`.
4. Actualización optimista (`onMutate`, `cancelQueries`, `setQueriesData`, rollback) en asientos, viajeros y tours.

**Organización y dependencias** (auditoría de arquitectura, 2026-11-14):

- Una feature puede usar componentes, hooks o schemas de otra, pero **sin ciclos** (hoy: `tour-dashboard` → `settings`, `statements`, `travelers`, `vehicles`; `external-registration` → `statements`, `travelers`; `tours` → `settings`; `settings` → `auth`). Si dos features se necesitan mutuamente, lo común va a `shared/` o a una feature propia (como `statements`).
- `shared/`, `components/` y `lib/` **no importan de `features/`**. Un enum de contrato compartido va en `shared/constants/domain.constants.ts` (por ejemplo `FormStatus`).
- Cada hook vive en la feature cuya pantalla lo usa: las acciones del operador están en `tour-dashboard/hooks`, aunque llamen a `/bookings`; el portal público solo tiene el registro.
- Para agregar una funcionalidad del Centro de Control, ubica primero su subcarpeta (`header`, `passengers`, `finance`, `seating`, `mobile`).

**Al crear una mutación que afecta al Centro de Control**, invalida `TOUR_DASHBOARD_KEYS.detail(tourId)`. Algunas mutaciones invalidan `TOUR_DASHBOARD_KEYS.all` completo.

- `TOUR_DASHBOARD_KEYS` cuelga de `["tour-dashboard"]`, **no** de `["tours"]`: invalidar `TOUR_KEYS` no refresca el Centro de Control. Como se cachea 5 min y no se vuelve a pedir al recuperar el foco, cualquier mutación que cambie datos que el dashboard muestra (incluida la **edición del tour**: `staffCapacity`, capacidad, precio, anticipo, fechas, puntos de abordaje) debe invalidarlo explícitamente.
- Corregido el 2026-11-12: `useUpdateTour` no lo invalidaba, así que tras editar "Lugares bloqueados para staff" el croquis seguía recibiendo `staffCapacity = 0` hasta 5 min (la API respondía bien). Lo cubre `features/tours/hooks/__tests__/useUpdateTour.test.tsx`.

**Constantes y utilidades compartidas:** monedas y métodos de pago salen de `shared/constants/domain.constants.ts` (los schemas Zod usan `z.enum(CURRENCIES)` / `z.enum(PAYMENT_METHODS)`); no declares uniones `"MXN" | "USD"` a mano. Los enlaces `wa.me`, el magic link y la URL del folleto se arman con `shared/utils/share-links.util.ts`.

**Importes (formato único):** todo importe se muestra con `formatCurrency(value, { currency })` de [currency.util.ts](src/shared/utils/currency.util.ts), en pantallas, modales, KPIs, textos para compartir y PDF. Formato: `$1,000.00 MXN` / `$1,000.00 USD` (símbolo `$`, comas de miles, dos decimales y código al final; negativos `-$500.00 USD`; `null`/`NaN` → `$0.00 <divisa>`). Reglas:

- Pasa **siempre** la divisa real del importe (`tour.currency`, `tourCurrency`, `payment.currency`); el `DEFAULT_CURRENCY` solo es un respaldo. No conviertas montos para mostrarlos.
- No concatenes el código ni el símbolo a mano (ya vienen incluidos) ni uses `toLocaleString`/`Intl.NumberFormat` para dinero. Un `+` decorativo de abono va fuera: `` `+${formatCurrency(x, { currency })}` ``.
- Los tipos de cambio (`TC aplicado: $17.20 MXN/USD`) no son importes y no pasan por esta función.
- Toda respuesta con importes trae la moneda del tour: `tourInfo.currency` en todos los estados del Magic Link, `currency` en el manifiesto y en cada viaje del historial del viajero. El LTV se muestra **por divisa** con `metrics.lifetimeValueByCurrency` (una línea por moneda); `metrics.lifetimeValue` suma divisas distintas y no debe mostrarse como importe.

**Cliente HTTP** ([src/lib/api-client.ts](src/lib/api-client.ts)):

- `withCredentials: true` (cookie httpOnly) y `timeout` de 10 s (`API_TIMEOUT_MS`). Las subidas de archivos (folleto en `useTours`, logotipo en `useAgencyBranding`) pasan `timeout: UPLOAD_TIMEOUT_MS` (120 s): con 10 s, un PDF de 5 MB en una conexión móvil lenta se cortaba (corregido el 2026-11-16). Toda subida nueva debe usarlo.
- El interceptor devuelve `response.data?.data ?? response.data` (hasta el 2026-11-14 usaba `||`, que devolvía el sobre completo con `{ data: 0 }`, `false` o `""`; con `{ data: null }` sigue devolviendo el sobre). Las listas paginadas del backend llegan como **array sin `pagination`**, y `useTours` y `useTravelers` piden **todas** las páginas con `fetchAllPages` (`shared/api/fetch-all-pages.ts`: `limit=100`, `offset` creciente hasta una página incompleta, tope de 50 páginas y sin duplicados por `id`) y filtran en el cliente (`useTourFilters`, `useTravelersFilter`). Hasta el 2026-11-16 solo pedían la primera página y del registro 101 en adelante nunca aparecían.
- Ante un 401 (excepto en `/auth/login`) redirige a `/login?expired=true`.
- Los errores se normalizan a `ApiError { status, message, code, issues }` y se recorta el prefijo `"body/campo "` de los mensajes de Fastify.

**Páginas públicas** (`register`, `p/[id]`): son Server Components que usan `fetch(\`${API_BASE_URL}/…\`, { cache: "no-store" })` (`lib/api-config`) directamente, no `apiClient`.

- Las interacciones de una página pública van en Client Components hijos (por ejemplo, `BrochureCallToAction` en `/p/[id]`), que sí usan `apiClient` + React Query (el `ReactQueryProvider` está en el layout raíz).
- `/register` elige la vista con un mapa `FlowViews[flowState]`, a partir de `GET /magic-tokens/:token/validate`.
- Las vistas reciben `{...validation.data, token}`.

**Formularios:**

- react-hook-form con `zodResolver(schema)`, normalmente con `mode: "onChange"`.
- **Reglas obligatorias por el React Compiler** (falla real del 2026-11-15 en Configuración → Agencia: el formulario mostraba lo escrito pero enviaba los valores con los que se cargó y no mostraba errores):
  - Datos que llegan de la API: usa la opción `values` de `useForm` (con `resetOptions: { keepDirtyValues: true }` si el usuario puede estar editando). **Nunca** `useEffect(() => form.reset(data))`.
  - Estado del formulario (`errors`, `isDirty`, `isValid`): léelo con `useFormState({ control })` **antes** de cualquier `return` temprano (carga, error). No leas `form.formState` después de un `return` temprano: el compilador memoriza la lectura y el botón Guardar o los errores dejan de actualizarse (le pasó a "Identidad Visual").
  - Valores observados: `useWatch`, no `form.watch` ni `watch` del contexto (en `TourBoardingSection`, `watch("transportModality")` quedaba memorizado y elegir "Hiking" no cambiaba la sección; corregido el 2026-11-15).
  - Ojo: si un componente usa `watch()`, el compilador **no lo compila** (lint `react-hooks/incompatible-library`: "Compilation Skipped") y corre como React normal. Por eso `RegisterPaymentModal` y `EditTravelerDrawer` funcionan con `useEffect` + `reset`. Si cambias su `watch` por `useWatch`, el componente pasará a compilarse: cambia también ese `reset` por `values` y corre sus pruebas.
  - Las pruebas compilan con el React Compiler (`vitest.config.ts`), así que estas fallas ya se detectan: `AgencyTab.save-flow.test.tsx` cubre el caso con React Query y react-hook-form reales.
- Los schemas están en `features/<x>/schemas/*.schema.ts`. Convención de nombres:
  - `XInput`: datos que el front envía a la API (cuerpo de la petición o variables de la mutación). Si el formulario coincide con el cuerpo, el formulario también usa `XInput` (`LoginInput`, `TourInput`, `BookingInput`).
  - `XFormInput`: valores de un formulario que **no** coinciden con el cuerpo enviado (`QuickBookingFormInput` + `tourId` = `QuickBookingInput`; también `PreBookingFormInput`, `PaymentFormInput`, `EditTravelerFormInput`).
  - `XOutput`: respuestas de la API y sus partes anidadas (`TourOutput`, `TourDashboardOutput`, `TitularRowOutput`, `VehicleOutput`).
  - Los schemas de petición y respuesta se llaman `xInputSchema` / `xOutputSchema`. Los de validación de formulario conservan su nombre (`tourSchema`, `bookingFormSchema`).
  - No uses `DTO`, `Payload`, `Body`, `Result` ni `FormValues` como sufijo.
- Los schemas del front transforman los valores de los inputs (cadenas a números, `""` a `null`, fechas a `YYYY-MM-DD`) y **replican las reglas del backend**. Por ejemplo, para tours: el anticipo no puede superar el precio, la tarjeta exige `paymentLink`, el efectivo exige instrucciones de al menos 10 caracteres y debe haber al menos un punto de abordaje.
- Si cambias una regla, cámbiala en ambos repos.
- `TourForm` crea o actualiza el tour y **después** sube el folleto con `FormData` a `/tours/:id/brochure`.
  - Si la subida falla, el tour **ya está guardado**: se avisa con un toast y, al crear, se navega a `/tours/:id/edit` del tour nuevo. Así un segundo clic nunca crea un duplicado. "Guardar" sigue deshabilitado mientras se sube el folleto (`isProcessing` incluye `isUploading`).
  - "Limpiar" (`handleReset`) reinicia los campos **y** el PDF adjunto o existente, que viven en estado aparte del formulario.
  - Al editar, el formulario se valida al cargar (`form.trigger()`), y el pie muestra "Completa o corrige los campos marcados para poder guardar." mientras sea inválido. Así un tour guardado por API que incumple una regla solo del front no deja el botón deshabilitado sin explicación.
  - Usa `useWatch` (no `form.watch`), por compatibilidad con el React Compiler. Las secciones están en `form-sections/` (`TourGeneralSection`, `TourBoardingSection`, `TourFinanceSection` —moneda, precio, anticipo, métodos de cobro y sus datos—, `TourInstructionsField` y `TourAssetSection`). Desde el 2026-11-14 las finanzas vuelven a ser una sección (antes vivían dentro de `TourForm`); `TourForm` conserva el estado, las validaciones cruzadas y el guardado.

**Componentes:**

- `app/` solo compone. La lógica y la UI viven en `features/`. Los componentes de presentación reciben props, y los contenedores (`TourDashboardView`, páginas) usan los hooks.
- **Versión móvil:** variantes dedicadas (`features/*/components/mobile/*`, `*MobileCardList`) en lugar de una sola tabla responsiva.
  - Las variantes de escritorio y móvil de una misma pantalla **comparten el estado de interfaz** del contenedor; no dupliques un `useState` por tamaño de pantalla. Ejemplo: el Centro de Control tiene **una sola** pestaña activa (`activeTab: DashboardTab`, de [constants/dashboard-tabs.ts](src/features/tour-dashboard/constants/dashboard-tabs.ts)) que usan `TourTabsNav` y `MobileTabsNav`. Antes había `activeTab` y `mobileTab` y se desincronizaban.
  - En ambos tamaños, «Asignar asiento» (con vehículo) y asignar un vehículo llevan a la pestaña `"seatmap"`, porque la asignación de asientos solo existe en el croquis.
- Los estados de la UI salen de [status-dictionaries.config.ts](src/shared/utils/config/status-dictionaries.config.ts): `PAYMENT_STATUS_DICT`, `FORM_STATUS_DICT`, `PAYMENT_METHOD_DICT` (etiquetas cortas del operador: "SPEI", "EFECTIVO"…), `PAYMENT_METHOD_LABEL_DICT` + `getPaymentMethodText` (texto para el cliente: "Transferencia", "Efectivo", "Tarjeta / Link"; lo usan el estado de cuenta del Magic Link y el PDF) y `PASSENGER_ROLE_DICT` ("Titular" / "Acompañante"). Úsalos en lugar de escribir las etiquetas a mano.
- **Enums de dominio:** nunca escribas sus valores como texto (`"TITULAR"`, `"MXN"`, …). Usa la tupla para Zod (`z.enum(PASSENGER_ROLES)`, `z.literal(PASSENGER_ROLE.COMPANION)`), el tipo (`PassengerRole`) y el objeto por nombre para comparar (`role === PASSENGER_ROLE.TITULAR`). `passengerRoleSchema` (en `tour-dashboard.schema.ts`) es el schema Zod compartido por el dashboard y la transferencia.
- Las confirmaciones destructivas usan `components/shared/ConfirmDialog.tsx` o los diálogos de `tour-dashboard`.
- El logotipo de la agencia se dibuja siempre con `components/shared/AgencyLogo.tsx` (`logoPath` de la API → `buildApiPublicFileUrl`; sin logo o si el archivo no carga, muestra la brújula). Lo usan el Sidebar y el menú móvil (`useSession().data.agencyLogoPath`) y todas las vistas del Magic Link (vía `PublicBookingHeader`) y la pantalla de reserva cancelada, además del encabezado del folleto público (`p/[id]`, `tour.agency.logoPath`). Las vistas del Magic Link reciben la prop `agencyLogoPath` desde `register/page.tsx` (`meta.agency.logoPath`).

## Guías interactivas (driver.js)

- `/tours`, `/travelers`, `/settings` (una parada por pestaña; `SettingsGuideButton`, porque la página es Server Component) y el Centro de Control (`/tours/[id]`), en escritorio y celular, tienen una guía paso a paso. Cada paso señala un elemento con `data-tour={TOUR_TARGET.X}`; escritorio y celular llevan la misma marca y `findVisibleTourTarget` elige el visible. ## Rutas, navegación y sesión

- Menú en [navigation.ts](src/shared/utils/config/navigation.ts): Tours (`/tours`), Viajeros (`/travelers`) y Configuración (`/settings`).
- [src/proxy.ts](src/proxy.ts):
  - sin cookie en `/tours*`, `/travelers*`, `/settings*` o `/pdf-tour*` (`PROTECTED_PREFIXES`) → `/login`;
  - con cookie en `/login` → `/tours`, salvo `?expired=true`, que borra la cookie.

  Esas mismas rutas llevan `Cache-Control: no-store` desde `headers()` de [next.config.ts](next.config.ts) (el proxy no puede fijarla: Next la sobrescribe; en producción respeta la de `next.config`). Mantén ambas listas sincronizadas. El proxy solo verifica que exista la cookie, no que el JWT siga vigente.

- **Encabezados de seguridad** (2026-11-13, `headers()` de `next.config.ts`, regla `/:path*`): `X-Frame-Options: DENY` + `Content-Security-Policy: frame-ancestors 'none'` (la app no se puede incrustar en iframes), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` (el token del Magic Link no viaja a wa.me ni al link de pago) y `Permissions-Policy`. Los cubre `src/__tests__/next-config.security.test.ts`. Si alguna vez se incrusta una página en un iframe propio, hay que ajustar esta regla.
- **Errores 409/429 de la API:** el interceptor ya muestra `{ error }`, así que "Esta reserva ya fue registrada…" (registro repetido del Magic Link) y "Demasiados intentos…" (límite de intentos) llegan al toast sin código extra.
- Sesión: `useSession()` (`GET /auth/me`, `staleTime` de 15 min, sin reintento) en el Header y el Sidebar. Login, logout y cambio de contraseña están en `features/auth/hooks/useAuth.ts`, y la sesión en `features/auth/hooks/useSession.ts`. El login usa `router.replace("/tours")`; el **logout hace una navegación dura** (`window.location.replace("/login")`, o `?expired=true` si la API falla) porque la Client Cache de Next reutiliza las páginas en atrás/adelante sin pasar por el proxy, y con `router.replace` la página privada se volvía a pintar al pulsar «Atrás». El 401 del interceptor también usa `location.replace`. No vuelvas a `router.push/replace` para salir de la sesión. No hay contexto de auth ni guarda de roles en la UI.

## Compatibilidad con el backend

- Antes de consumir un endpoint, verifícalo en `tripagent-api/src/modules/*/…routes.ts`. **No inventes rutas.**
- Los nombres de enums y campos deben coincidir con `tripagent-api/src/db/schema.ts`. El `tour-dashboard.schema.ts` del front tiene enums desalineados (`ADVANCE`, `PENDING_VALIDATION`, `ACTIVO`) frente a los reales (`PARTIAL`, `REFUNDED`, `PRÓXIMO`, `EN CURSO`). La respuesta del dashboard no se valida con `parse`; el manifiesto sí (`tourManifestOutputSchema.parse`), así que un cambio en esa respuesta puede romper la página.
- **URLs de archivos de la API:** el backend guarda `brochureUrl = "/uploads/brochures/…"` y lo sirve en `<origen API>/public/uploads/…`, **sin** `/api`.
  - Usa `buildApiPublicFileUrl(path)` (`shared/utils/share-links.util.ts`), que toma el origen de `NEXT_PUBLIC_API_URL` y le agrega `/public` + la ruta. `TourForm` ya lo usa.
  - `p/[id]` ya no tiene una IP fija: usa `API_BASE_URL` y `buildApiPublicFileUrl`.
- `GET /magic-tokens/:token/lookup-traveler` (público) devuelve `{ fullName, email, emergencyContactName, emergencyContactPhone, birthDate }`, sin notas médicas (el hook lo tipa como `TravelerOutput`). El titular autocompleta nombre, correo y fecha; el acompañante, nombre, notas médicas (que quedan vacías porque la API no las envía) y fecha.
- **Reglas de negocio que vienen calculadas del backend (no recalcular en el front):**
  - **Derecho a asiento:** `titular.hasSeatRight` (lo pagado cubre `requiredDeposit` = anticipo por persona × lugares). Controla el panel "Faltan por acomodar" (`TourDashboardView`), el botón "[ Asignar Asiento ]" y la etiqueta "Requiere anticipo" (`TravelerGroup`, `mobile/BookingCard`). La API rechaza con 409 una asignación sin anticipo cubierto.
    - **Asiento conservado sin anticipo** (regla 8 de `../CLAUDE.md`, 2026-11-13): si el grupo pierde el derecho a asiento, la API no libera el asiento. Con `seatLabel` asignado y `hasSeatRight` falso, `TravelerGroup` (titular y acompañantes) y `mobile/BookingCard` muestran `SeatWithoutDepositBadge` ("⚠ 12 · Asiento asignado sin anticipo cubierto"; en el acompañante móvil, la variante `compact`, "Sin anticipo"). Antes, la tabla de escritorio ocultaba el asiento detrás de "Requiere anticipo".
  - **Antigüedad del apartado sin pago** (regla 13 de `../CLAUDE.md`): `titular.bookedAt` (fecha del apartado) alimenta `UnpaidHoldAge` ("Apartado hace 50h sin pago", en la columna de pagos y en la tarjeta móvil). Solo aparece con `paidAmount ≤ 0` y saldo > 0. Desde `UNPAID_HOLD_REVIEW_HOURS` (48, `tour-dashboard/constants/unpaid-hold.ts`) se pinta en rojo, y el contador se actualiza cada minuto. Es una ayuda visual: no cancela nada.
  - **Confirmación:** `bookingStatus` (`CONFIRMED` = anticipo cubierto + formulario lleno). El distintivo "Viaje confirmado" del estado de cuenta (`PartialPaymentView`) solo aparece con `CONFIRMED`; si no, se muestra "Pendiente de anticipo".
  - **Abonos visibles para el cliente:** el `paymentHistory` del Magic Link ya llega sin anulaciones. El comprobante PDF generado desde el Centro de Control (`DashboardTravelerTable`) aplica el mismo filtro (excluye `REFUND` y el abono referenciado con `(Ref: <id>)`).
  - **Pase de abordaje (`PAID`):** `PaidBookingView` + `TravelerTicketCard` (tipos en `schemas/paid-booking.schema.ts`). Oculta pasajeros `CANCELLED`, pone al titular como viajero 1 y muestra el punto y la hora de `boardingPointDetails` (si no hay coincidencia, el texto guardado salvo que sea un UUID). Un punto de abordaje solo tiene una hora: no hay "salida puntual" ni referencia física. WhatsApp antepone `52` solo si el teléfono de la agencia tiene 10 dígitos.
  - **El Magic Link no vence:** no existe vista de enlace expirado en `/register` ni avisos de "24 horas".
  - **Cupo y ocupación:** `occupancy.max` del dashboard y `sellableCapacity` del listado de tours ya son la **capacidad vendible** (`maxCapacity − staffCapacity`); `currentOccupancy` / `occupancy.current` son los lugares ocupados (todas las reservas no canceladas). El folleto recibe `availability { sellableCapacity, occupiedSeats, availableSeats, isBookable }` y la muestra sin recalcular. La única resta que hace el front es la ayuda del formulario de tour ("Lugares disponibles para venta al público: X"), que previsualiza los valores capturados.
  - **Sobreventa:** la API responde 409 cuando no hay cupo (apartado rápido, pre-reserva, agregar lugar). El front muestra el mensaje del servidor.
- **Identidad visual y estado de cuenta PDF** (regla 16 de `../CLAUDE.md`):
  - **Configuración → "Identidad Visual & PDFs"** (`?tab=branding`, `BrandingSettingsCard`): el logotipo se sube **al seleccionarlo** (`useUploadAgencyLogo` → `POST /agencies/logo`, `FormData` con campo `file`) y se quita con `useRemoveAgencyLogo`. `LogoUploader` valida PNG/JPEG ≤ 2 MB antes de subir (`validateLogoFile`). Los colores (`ColorPickerInput`: selector nativo + hex + `SUGGESTED_BRAND_COLORS`; el acento es opcional, con "Quitar" → `null` y el secundario como respaldo vía `fallbackColor`) se guardan con "Guardar Configuración" (`useUpdateBranding`, optimista con rollback). El formulario se sincroniza con la API mediante la opción `values` de react-hook-form (sin `useEffect`). Una vista previa en vivo muestra el encabezado del PDF.
  - El logo se muestra con `buildApiPublicFileUrl(logoPath)` (`<origen API>/public/uploads/logos/…`). `agencies.logoUrl` ya no existe: es `logoPath` y solo cambia por esos endpoints (no por `PATCH /agencies`).
  - **Estado de cuenta PDF** (`features/statements/pdf/payment-receipt.pdf.ts`): contrato `StatementPDFData` (`agency` con `accentColor`, `tour`, `passengers: PassengerItem[]`, `financials { currency, totalAmount, paidAmount, balanceDue, payments: PaymentItem[] }`, `policies?: { tour, agency }`, `emissionDate?`). `createPaymentReceiptDocument(data, logo)` arma el documento (síncrono, probado) y `generatePartialPaymentReceiptPDF(data)` carga `agency.logoUrl` (DataURI o URL; si falla, sale sin logo) y guarda `estado-de-cuenta-<tour>.pdf`. `buildStatementPayments` ordena los abonos y deriva el concepto (la base no lo guarda). **Recibe todo por props**: no consulta la API. **El número de tarjeta no se imprime** (decisión del PM, 2026-11-13): `bankInfo` solo tiene `bankName`, `accountHolder` y `clabe`, y ni `buildMagicLinkStatement` ni `TourDashboardView` lo envían. Las pantallas del Magic Link sí muestran la tarjeta.
    - **Cliente (Magic Link):** `buildMagicLinkStatement` (`pdf/magic-link-statement.ts`) es la única conversión del payload al PDF, y `DownloadStatementButton` ("Descargar Estado de Cuenta en PDF", con estado de carga y toasts) la usa en `PartialPaymentView` y en `PaidBookingView` (pase de abordaje). El botón recibe la prop `source` (datos planos del payload) y arma el PDF al hacer clic: **no recibe funciones**, porque `PaidBookingView` es un Server Component y Next solo permite pasar props serializables a un componente cliente (una función como prop rompe `/register` con _"Functions cannot be passed directly to Client Components"_). `schemas/paid-booking.schema.ts` declara los campos del payload que el PDF necesita (`paymentHistory`, `groupSize`, banco, marca, `agency.policies` y `tourInfo.postPaymentInstructions`).
    - **Operador:** `DashboardTravelerTable` (props `statementAgency` —incluye `policies`—, `tourPostPaymentInstructions`, `tourDepartureDate`, `tourReturnDate`); `TourDashboardView` los arma con `useAgency()` (incluye `policies`), `useAgencyBranding()` (incluye `accentColor`) y el dashboard (`returnDate`, `postPaymentInstructions`).
